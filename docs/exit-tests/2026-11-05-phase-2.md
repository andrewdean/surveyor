# Phase 2 exit test: context packs for ten Causeway tasks, and five invariants

The RFD's Phase 2 exit test reads: `context_pack` for ten Causeway tasks fits a
30 thousand token budget and a reviewer accepts each as sufficient; five invariants
pass on Causeway `main` and fail on three planted violations. This document records
the run. `PLAN-surveyor-phase-2.md`, beside the RFD, says how the ten tasks and the
five invariants were chosen.

**Where it stands.** All ten packs fit the budget: the largest is 29,982 tokens under
the `cl100k_base` encoding, and the planner fills every budget to within a hundred
tokens, because every task had hundreds of candidates more than the budget holds.
Against the answer key, the symbols and files each merged change touched, the packs
carry 54 of the 100 key entries where today's `query_graph` answer carries 36; two
packs carry their whole key and one carries almost none. The reviewer's column of
Table 1 is empty: Andrew reads each pack under `raw/2026-11-05-phase-2-packs/` and
says whether an agent handed it could do the task. The invariant half is the next
stage and is not yet run.

## Setup

| Item | Value |
|---|---|
| Tasks | `docs/eval/causeway-tasks.toml`: ten merged pull requests of andrewdean/causeway (1014 to 1073), each written as the task an agent would receive, with a key of the identifiers that existed before the change and the files it touched |
| Trees | each task's base commit (the merge commit's parent), as a detached worktree of a shared scratch clone under `causeway-worktrees/surveyor-phase-2-bases/`; the Causeway checkout itself was read, never written |
| Stores | one per base, name tier only, `examples/causeway-profile/surveyor.toml`, built by `docs/eval/causeway-task-stores.sh` (release build of `a984fc5`, 8 to 42 s each) |

| Baseline | the same eval with `--source query-graph`: the MCP tool's exact answer to the task text, five seeds with their direct relations, counted the same way |
| Scoring | a key identifier counts when the pack carries its card; a key file when the pack carries any node in it; tokens are `cl100k_base` over the Markdown an agent reads |

What the packs get right: the tasks that name a symbol, a crate or a package
(`Relay::drain`, `causeway-db-core`, `@causeway/rpc-access`) seed on it at full
score and the pack opens with its card, its callers and its source; the tasks whose
words match a file's names seed in that file and the pack brings the file's other
members, the impl and the type that own them, and the tests; and a change that spans
languages (task 10: proto, Rust and the Node page) is followed across them through
the `CALLS` and `IMPORTS` edges the graph holds.

What they miss, by task, with the cause as far as I could trace it:

- Task 3 (1 of 11): the task's words find the migration machinery in
  `workspace_migrations.rs`, but the function that has to change,
  `causeway_db_core::init`, neither calls nor is called by it (it runs the embedded
  migrations through `sqlx::migrate!`), and "initialisation" does not stem to the
  doc's "Initializes". The crate name seeds the package, but the package contains
  130 files, most of them migrations, so its source files get a small share each.
  This is the case for the vector half or for a better owner walk from a package to
  its source files; neither is in this stage.
- Task 6 (3 of 11): the Maud views that embed the JavaScript sending `dataset.load`
  hold it in string constants (`SEGMENT`), which no edge connects to the browser bus;
  only text could reach them, and the task's words are the bus's.
- Task 7 (6 of 13, one fewer than the baseline): `RouteAccess`, `rpc::routes` and the
  Connect proxy handler are two hops from the seeds through `build_router`, which
  calls twenty-eight functions, so each gets less than half of the hop's score; the
  baseline's five seeds happened to include one of them directly.
- Tasks 1, 2, 8, 10: the keys missed are either files with no symbols the graph links
  (`moon.yml`, `Cargo.toml`, the proto file, a test file the seeds do not touch) or
  the Rust behind a host function (`http.rs::build` behind the Rhai `http::get`),
  which is three hops from the script.

Cost: on Andrew's Causeway store (61,781 nodes, the thirteen rules loaded) the
release build loads the graph in 0.3 s and plans a 30,000 token pack in 56 ms; the
whole `surveyor context` command, text index, rule run and tokenizer included, takes
about five seconds of wall clock.

How the planner got here is in `docs/eval/README.md` ("Context-pack eval"): six
measured versions between the first run (45 of 100, four packs over budget) and this
one. The last change, lifting each candidate by its own match against the task's
words, is the reranking the plan's stage 5 describes; it is in, and the remaining
misses above are graph reach and vocabulary, not ranking.

## 2. Five invariants, three planted violations

Not yet run; stage 4 of the plan. The five rules (`06-component-cross-deps`,
`10-server-rpc-deps`, `11-server-service-impls`, `13-island-cross-refs`,
`04-runtime-env-resource-ctors`) pass on today's Causeway store, as the plan records;
the planted clone and the scripted run come next.

## 3. What this test does not cover

The packs are measured against a key of what the merged change touched, which is a
proxy for sufficiency, not the reviewer's judgment the exit test asks for; the
reviewer's column is Andrew's. The stores are name tier only (no SCIP indexes), as
the per-base stores were built without the indexes, which describe today's tree;
Andrew's own store carries them, and a pack built there resolves the same edges with
higher confidence. Token counts are `cl100k_base`, a proxy for Claude's tokenizer;
the byte column is there so the margin can be judged against any encoding.
